## 문제 제기

Source 문서는 이후 새로운 Synthesis를 만들 때 원문을 재열람하지 않아도 주요 사실·맥락·근거를 재구성할 만큼 충실해야 한다. 그런데 최근 김성수 대법관 성범죄 양형 관련 기사 7건을 처리하는 과정에서 다음 문제가 드러났다.

1. 처음에는 Source 본문이 지나치게 짧고, 사건별 사실·판결 이유·해명·맥락·구체적 인용 위치를 담지 못해 새로운 분석에 충분하지 않았다.
2. 이를 보완하면서 모든 문서에 임의의 `## 근거 및 확인 상태` 절을 추가했다. `source_path`, `ingested_at` 등 frontmatter와 중복되며, 원자료의 내용보다 에이전트의 작업 상태 설명이 커졌다.
3. 본문 기반 상세 요약과 원문 전문/원본 파일 보존의 차이를 처음부터 일관되게 표현하지 못했다.
4. 검색 가능 여부만 확인하고도 새로운 Synthesis에 필요한 정보 밀도·주장별 증거 연결성까지 검증했다고 간주하기 쉬웠다.
5. 현행 `_schema.md`는 `cogvault ingest`가 자동으로 Source를 생성하고 에이전트는 수동 인제스트를 하지 않는다고 규정한다. 실제로는 에이전트가 `wiki_write`로 `sources/` 아래 문서를 직접 생성·덮어썼다. **스키마 규칙과 실행 경로가 불일치**한다.

## 개선 요청

- **인제스트 책임 명확화:** `cogvault ingest`가 수행할 일과 에이전트가 `wiki_write`로 할 수 있는 보강 작업의 경계를 명세하고 실제 도구로 지원할 것. 원문을 읽은 에이전트가 인제스트 요청을 제출할 공식 인터페이스가 없다면 제공 여부 검토.
- **내용 중심 Source 템플릿:** 기사 종류에 따라 보도 일시·사건번호(있는 경우)·1심/항소심 결과·양형 사유·사정변경·당사자 해명·데이터 산출 기준·논쟁점 등 추출할 항목을 정하되, **없는 정보는 빈칸을 추측으로 채우지 말 것**. 고정 섹션 남발을 피할 것.
- **근거 추적성:** 개별 중요한 사실에서 원문 단락, 소제목, 페이지, 인용 위치 등으로 거슬러 갈 수 있는 방식 제공. 원문이 없는 경우 명확히 표시.
- **메타데이터 분리:** URL·수집일·입력 파일·추출 상태·검증 수준·원본 보존 상태 등은 되도록 frontmatter 또는 일관된 시스템 필드로 관리. 본문에 `근거 및 확인 상태` 같은 장황한 공통 절을 무조건 삽입하지 말 것.
- **인제스트 상태 구분:** `metadata_only`, `body_read`, `structured_summary`, `raw_archived`, `judgment_verified` 등을 정확히 구분. 요약 저장을 원문 파일 보존이라고 표시하지 말 것.
- **품질 검사:** Source 검색 인덱싱 성공뿐 아니라 누락된 핵심 사실, 주장의 출처 추적, 원자료와 종합문서의 구분, Synthesis 재사용 가능성을 검사할 기준 마련.
- **중복 방지:** 기존 원문·Source가 존재하면 무조건 새 페이지 생성보다 갱신/연결/중복 점검 우선.

## 기대하는 동작

사용자가 기사 원문을 제공하거나 읽을 수 있게 된 경우, 인제스트 파이프라인이 원문 기반의 충분한 사실·맥락을 구조화하여 Source에 남긴다. 검증/보존 상태는 정규화된 메타데이터로 추적하고, Source 본문은 사건의 내용과 근거에 집중한다. 이후 다른 질문으로 새로운 Synthesis를 생성할 때 같은 기사를 대부분 다시 읽지 않아도 되고, 중요한 주장만 원문으로 역추적해 확인할 수 있어야 한다.

## 처리 상태

- **검토 대기.** 사용자가 확인 후 이 피드백 문서를 직접 삭제할 예정.
